Considering Future Node Expansion
  You raise a very valid and strong point. Using separate tables for  canvases  and  canvas_nodes  is indeed the correct path if you plan to extend node capabilities in the future.

  Here is a breakdown of why separate tables are better for your vision, followed by how we can clean up the current rough edges:

  ### 1. Benefits of Separate Tables (Relational Schema)

  • Cross-Canvas Search & Querying: If nodes are stored as individual database rows in a  canvas_nodes  table, you can easily query them globally. For instance, you could search for "all
  YouTube videos saved across all my canvases" or "the most commonly used code snippets." Doing this with a JSONB document inside an  ideas  row would require complex, slow JSON path
  queries.
  • Node Referencing & Reuse: In a relational model, each node has a unique  UUID . This allows you to reference a node from another canvas, link ideas together, or create a true graph
  of thoughts without duplicating data.
  • Polymorphic Extensions: In the future, if you want nodes to support features like version history, node-specific comments, likes, or collaborative ownership, separate tables make it
  easy to establish these foreign-key relations.
  • Conflict-Free Real-Time Editing: If multiple users edit the same canvas concurrently (e.g. via Supabase Realtime), updating individual rows (moving Node A while someone else edits
  Node B) is clean. With a single JSONB column, concurrent users would overwrite the entire canvas payload, leading to race conditions.
  ──────
  ### 2. How to Fix the "Rough Edges" in the Relational Schema

  Since separate tables fit your long-term roadmap, we should keep them but address the current code quality and schema discrepancies:

  1. Unify the SQL Schemas:
      • Clean up the duplicate SQL definitions in  supabase SQL/canvas.sql  and  supabase SQL/items.sql .
      • Update  supabase_setup.sql  to represent the single canonical database configuration.
      • Introduce a  connections   JSONB  column directly to the  canvases  table so we don't have to hack connections into the  description  text field (e.g., no more 
      description__CONNECTIONS__  strings).
  2. Clean up the "Destructive Sync":
      • Currently, updating a canvas deletes all its nodes and re-inserts them. This is slow and risky.
      • Fix: We will implement a clean sync in server.ts. When updating a canvas, we will:
          • Detect nodes that are no longer in the payload and delete them.
          • Upsert (Insert or Update) the remaining nodes so existing nodes are updated in-place (preserving their database IDs and creation timestamps).

  3. Field Mapping & Standardization:
      • We will standardise the column-to-property conversion on the backend. When returning canvases and nodes, the backend will map snake_case columns ( canvas_id ,  item_id , 
      code_snippet ,  resource_url ,  resource_title ) cleanly to camelCase properties ( canvasId ,  itemId ,  codeSnippet ,  resourceUrl ,  resourceTitle ) expected by the React
      frontend.
